## N1 (major). zero-arm handle は capability 制御の抜け穴 — 設計 3 本柱の 3 が破れる

```vibe
fn needs_fs() -> String with Fs {
  Fs::read_file("config.toml")
}

fn f() -> String {              // row 無し。「純粋」を名乗れる
  handle { needs_fs() } with Fs { }
}
```

`vibe check` は clean、実行すると **本物の `Fs::read_file` host import が走る**
(存在しないパスを渡して ENOENT で確認)。機構の連鎖 (code-read):

1. パーサは arm ゼロの handle を受理する (`parser_expr_dispatch.vibe:1171`)
2. `EHandle` は handled effect 名を**保持していない** — `with Fs` と読んだ名前は
   arm パターンの qualify にだけ使われ、checker は `arms[0]` から effect を
   逆算する。arm が無いと `collect_handle_effects([]) = []`
3. `checker_effects.vibe:2106-2110` で `body_in_handle = true` になり、body 内の
   **全** effect 要求診断が抑止される (`&& !in_handle` が 6 箇所)
4. codegen では zero-arm handle は body そのものにコンパイルされる
   (`compile_expr_tail6.vibe:222/377`)

つまり `handle .. with <何でも> { }` は「row からラベルを消すが、放電は何も
しない」フィルタとして機能する。capability を row が運ぶという pillar 3 の前提
(「認可は最早フェーズで一回だけ、run 中 authority 不変」) がソースレベルで
迂回できる。`--allow-*` の const-fold + DCE より上流の穴。

なお wildcard arm (`with Fs { _ => resume("fake") }`) で builtin 呼び出しを
包んだ場合は適格性エラーになるが、そのメッセージは
`handle of effect '<catch-all>' cannot be compiled here...` — **内部
placeholder `<catch-all>` がユーザー診断に漏れている** (実測。
`inline_direct_perform.vibe:2448-2453`)。同根: EHandle が effect 名を持たない。

**提案**: EHandle に parse 時の effect 名を持たせる。これ 1 つで (a) zero-arm
の row 抜け穴、(b) `<catch-all>` 漏れ、(c) arm からの effect 逆算、の 3 つが
同時に閉じる。

## N2 (major). 値位置の `for` は「checker は Array と言い、desugar は Unit を作る」

checker は `EForIn` を `CtArray(bodyType)` に付ける (`checker.vibe:6535`)。しかし
iterand が builtin Array/String/Map **以外** (pull closure・trait iterator・
HostStream・await iterator) のとき、`desugar_trait_dict.vibe` (`:2833,2878,2916,2943`)
は全体を **Unit 値の `EWhile`** に置き換える。値位置で使うと束縛には i64 0 が
入り、それが配列 pointer として再解釈される。実測:

```vibe
let counter = [0]
let pull = () -> Option[Int] {
  Array::set(counter, 0, counter[0] + 1)
  if counter[0] > 3 { None } else { Some(counter[0]) }
}
let xs = for b in pull { b * 10 }   // 期待 [10, 20, 30]
// 実測: Array::length(xs) = 2、要素は -864691128371249152 と 5、xs[2] は trap
```

cheatsheet の Control Flow 節 (`:436`) はこの pull closure 形を正規の形として
載せているが、```vibe skip ブロックなので doctest に検査されていない。
既存テストが全部「文位置 + 外側 mut 蓄積」で書かれているため
(`fixtures/trait_iterator_test.vibe:89-105` ほか)、値位置の穴は一度も
踏まれていない。

**提案**: 短期は「非 Array iterand の `for` は値位置で診断」(ADR-0099 D3 の
前倒し)。iterand が分類不能なら黙って sync ループに落とす現状
(`checker_effects.vibe:328-330` が自認) も同じ D3 で閉じる。

## N3 (major). `break` — 改行非依存 + payload 未評価破棄 + spec の虚偽

3 つの独立した問題が同じ場所に重なっている:

1. **payload は改行を見ずに貪欲に読まれる。** 改行はトークンではない
   (`TNewline` が存在しない) ので、`parse_break_primary` は次トークンが
   `}` `;` EOF でなければ break 値として式を読む。実測:

   ```vibe
   let s = loop (i = 0) {
     if i > 2 {
       break
       i * 100        // ← dead code のつもりが break の payload になる
     }
     continue(i + 1)
   }
   // s == 300 (この行が無ければ 0)
   ```

2. **`while` / 裸 `loop` の `break v` は v を評価せず捨てる。** checker は
   `v` を型付けした後 `CtUnit` を返し (`checker.vibe:6825-6831`)、両 backend
   とも payload を emit しない (`compile_expr_tail3.vibe:290-293`,
   `backend_expr.vibe:1507-1511`)。副作用も消える。
3. **spec が誤っている。** `docs/spec/syntax.md:435` は「`break Expr` returns
   a value from `loop` / `while`」— 実際に値が返るのはパラメータ付き `loop`
   だけ (パーサが `__loop_result` への代入に desugar するから)。この動作を
   固定する fixture は無い (全 fixture がパラメータ付き形か bare break)。

さらに裸 `loop { }` はパーサで `EWhile(EBool(true))` になり、パラメータ付き
`loop (..)` は `ELetMut` 連鎖になる — **同じキーワードの 2 つの綴りが別の
文法クラスに落ち**、`loop { .. } - 1` は 2 文、`loop (i=0) { .. } - 1` は減算に
parse される (code-read: `parser_expr_core.vibe:570-580`)。おまけに
`__loop_result` は魔法の名前で、ユーザーが `let mut __loop_result = 0` と
書くと初期化子の型ではなく fresh var が付く (`checker.vibe:3139-3155`)。
S8 (裸 break 時の placeholder 0 の型再解釈、実測) もこの desugar の穴。

**提案**: (a) `while`/裸 `loop` 内の `break v` は「この loop 形は値を返さない」
という located error にする (黙って捨てるのが最悪)。(b) `break` の payload は
同一行に限る (改行を挟んだら bare break)。(c) spec の当該行を直す。

## N4 (major). `==` — cheatsheet の境界記述は両方向に古く、未文書の残存穴がある

ADR-0097 の「全文脈構造的」への移行は前進しているが、cheatsheet

| 関数戻り値の配列 `make() == make()` | 参照 | 参照のまま (**false**) |
| tuple ごと戻した配列 | 参照 | 参照のまま (**false**) |
| 空リテラル束縛 `let e1 = []` | 参照 | 参照のまま — `e1 == e2` が **false** |

「3 文脈は同じ答えを返す」(`cheatsheet.md:291`) は関数戻り値のケースがある限り
誤り。残りの中では **関数戻り値** が最頻出の形 (2 つの呼び出し結果の比較) で、
`let e1 = []` の false は初見殺し。

> **r6.1 訂正 (PR #1684 レビュー指摘、再測定済み)**: 当初この表は「入れ子・
> struct 要素・erased tyvar の 3 ケースが直った」としていたが、**入れ子配列が
> 構造的になるのは束縛時に shape が記録される let 束縛経由だけ**で、注釈付き
> パラメータ経由 (`x: Array[Array[Int]]`) は今も参照等価に落ちる (実測)。
> `eq_elem_name_dispatchable` (`desugar_trait_dict.vibe:6438`) がスカラー名しか
> 通さないという指摘どおり。つまり名前経由の一般則は「要素が スカラー /
> equals を持つ struct・enum / Eq dict 付き型変数なら構造的、**入れ子配列は
> 不可**」で、リテラル可視の束縛だけが別レーンで救われている。struct 要素と
> erased `[T: Eq]` はパラメータ経由でも構造的 (再測定で確認、記載どおり)。

**提案**: cheatsheet の当該節を実測で書き直し (直った 2 つを消し、Option
payload / Float / 入れ子×パラメータを足す)、fn-return / tuple-return /
empty-literal / Option payload / nested-via-name を 1 つの P0 issue として
ADR-0097 の残作業に紐付ける (→ #1681)。

## N5 (major). slice 構文は文書化されておらず、型もない

パーサは `e[:]` `e[:end]` `e[start:]` `e[start:end]` の 4 形を受理して
`__slice(e, start, end)` に desugar する (`parser_expr_core.vibe:484-529`) が:

- `docs/spec/syntax.md` の indexing 節にも cheatsheet の演算子表にも **slice は
  存在しない**。一方 prelude はこれで書かれている (`string_head`/`string_take`
  等、`lib/@vibe/prelude/string.vibe`)
- `__slice` の宣言は `CtFn([CtUnknown, CtInt, CtInt], CtUnknown)`
  (`checker/builtins_misc.vibe:102-107`) — receiver も**戻り値も** `CtUnknown`
  で何とでも unify する。実測: `let n: Int = s[0:2]` が check clean、
  `println("\{n + 1}")` が `hell` を出力 (String が Int 束縛に流れ、`+ 1` が
  pointer 演算になっている)
- dispatch は実行時に heap header を嗅いで String/Bytes/Array を選ぶ
  (`compile_call.vibe:3009-3050`)

**提案**: `__slice` を receiver の型で 3 つに分ける (せめて戻り値を receiver と
同型に)。spec/cheatsheet に slice 構文を載せる。

## N6 (major). effect handler — 実装は 1 本道だが、その周りの記述と運用が壊れている

r6 で effect handler を集中的に見た。**コア機構 (evidence-passing、one-shot
resume、tail 制約、declared effect の arm 網羅性検査) 自体は健全**で、診断も
良いものが多い (実測: resume 非 tail、resume 二度呼び trap、handler arm 網羅性、
`with Error` の retire 誘導、未処理 effect の set-difference + hint)。問題は
その外側:

### 6a. capability ラベルの pun が silent-wrong (repo 自身のテストが被害者)

`lib/@vibe/fs/fs_test.vibe:1-7` と `lib/@vibe/fs/index_import_test.vibe:14-33` に
**構文的に同一の** `handle { .. } with Fs { ReadFile(..) => resume(..) }` があり、
前者の arm は**絶対に発火しない** (callee が builtin `Fs::read_file` 直呼びで
host import に直結) が、後者は発火する (callee が `perform Fs::ReadFile`)。
handle site からは判別不能で、fs_test.vibe は 7 行のコメントでそれを弁明して
いる。CamelCase↔snake_case の橋は手書き 22 行の表
(`core/builtin_name.vibe:3-33`、`Fs`/`Env`/`Profiler` のみ) で、この pun は
過去に実 miscompile も起こしている (`lib/@vibe/fs/fs.vibe:38-48` の
「wrapper fn にすると lowering を hijack する」、`lib/@vibe/http/http.vibe:3-18`
の #795)。

コンパイラ内部でも同じ pun が「row 抑止トリック」として 3 箇所で恒常運用されて
いる (`cache_underlying.vibe:43-58`、`module_graph_path.vibe:342-356`、
`cli/entry.vibe:9-37` — private `effect Env { Get(..) }` を宣言して builtin
`Env::get` を包み、絶対に発火しない arm で checker だけ黙らせる)。これは N1 の
zero-arm と同じ穴の「公式用法」化で、直すなら同時に直す必要がある。

**提案**: 「host provider ラベルへの handle は、body に perform 由来の到達が
1 つも無ければ診断」(vacuous-handle elimination が既にその判定をしている —
`inline_direct_perform.vibe:1059-1119` — 消す代わりに警告すればよい)。

### 6b. 適格性境界の記述が実装より厳しすぎる方向にずれている

cheatsheet 落とし穴節は「row 変数 (`with e`) 付き callee は compile error」と
書くが、実測では tail-resumptive handler なら通って正しく動く:

```vibe
fn call_thru(f: () -> Int with e) -> Int with e { f() }
// handle { call_thru(ask_once) } with Ask { Get() => resume(7) }  → 7 (実測 ok)
```

一方 capture-free で純粋な**ローカル closure 呼び出し**は reject される (実測、
#1511 の表どおり)。「row 多相の間接呼び出しは通るのに、静的に見えている
ローカル closure が通らない」— 規則が実装の lambda-lifting の都合
(#786 で top-level に持ち上がるかどうか) で決まっており、cheatsheet の表とも
`docs/language-tour/effects.vibe.md:109-111` (「top-level let の handle は
コンパイルできない」— r4 で反証済みの誤り、tour は未修正) とも食い違う。

### 6c. ADR-0050 が約束して実装に無いもの (code-read)

| ADR-0050 の約束 | 実装 |
|---|---|
| arm の guard (`Op(x) if x > 0 =>`) | パーサに経路が無い (`parse_handle_arm`)。使用例ゼロ |
| arm 網羅性は必須 | declared effect のみ、`arms[0]` から逆算。zero-arm は素通り (N1) |
| 非 tail `resume` は意味的に許容 | checker が一律 reject (#942) |
| 継続の保存・capture は禁止 | ADR-0076 Phase 3a で**逆転** — 今は suspend class の基盤 |

ADR-0084 (taxonomy) は自己申告どおり inert (`:11-16,82-84`)、`ParseRecur` は
ADR-0084 が代数 effect の代表例として挙げているのに、**宣言だけあって perform
も handle も 1 箇所も無い** — パーサは試した末に手動 closure 引き回しへ戻した。
教科書的ユースケースで自プロジェクトが effect を選ばなかった、という事実は
設計へのフィードバックとして重い。

### 6d. 生産コードでの代数 handler の実使用は実質 2 件

lib/ 生産コード (test/bench/probe 除く) の handle は Exception 84+2 件に対し、
代数 effect は: `TaskGroup::spawn_suspend` の `Async` (first-class resume の
唯一の実顧客)、`lsp_server.vibe` の `Lsp` (9-op の dispatch table — enum +
match で書ける形)、あとは 6a の row 抑止 pun が 3 件。**handler 機構
(13.9k 行の `inline_direct_perform.vibe`) の生産上の顧客はほぼ
`spawn_suspend` 1 件**。fixtures の effect corpus 222 件のうち gate に配線
されているのは 105 件で、known-uncompilable の 5 件が成功値を pin したまま
(`docs/effect-evidence-passing.md:1283-1292` が自認)、
`err_resume_in_error_arm.vibe` の needle は現行メッセージと不一致 (どこからも
実行されないので気づかれない)。

  (prelude 自身が「no host runtime implementation exists anywhere」と自認)
- 宣言だけの phantom builtin 群: f32/f64 スカラ命令ブロック、`int_ctz`
  (simd-api-design.md の中心 API、呼び出しゼロ)、builtin `Set::*`
  (ADR-0082 が「宣言だけの死んだ builtin」と自認)

labeled args (`x~:`)・optional args (`x?:`)・`let*`・`?`・`guard`・match arm
guard・or-pattern・`record {}`・`suberror`・`effectset`・`region`/`taskgroup`/

v128 SIMD surface。**`@vibe/concurrent` 全体 (1713 行 + checker_spawnable 759 行)

**予約だけして即 throw するトークン:** `raise` `do` `yield` `module` `use`。

**逆向きの死角:** `docs/cli-commands.md:198-270` は `fetch`/`init`/`finalize`/

**反復 surface (#1559 で既知) の実測補強:** `Iterator::*` の lib/ 生産呼び出し
**ゼロ** (`Iterator::map` の非 prelude ヒット 6 件は全部コメント)、

意味するので、1.0 freeze までに「凍結して出す/削る」の判断が要る。

## N8. 診断 — 新しく見つけた種別 (repair コーパス追加候補)

r5 で L 9/10 まで来た位置情報だが、プローブで新しい非配線クラスを踏んだ:

- **`loop` の continue arity エラーが 2 回出て、2 回とも位置が違う** (実測:
  continue が 9 行目にあるのに `line 5:1` と `line 7:3`)。メッセージ本文
  (#1284) は模範的なのに位置が台無し
- **位置なしクラス**: non-exhaustive match / non-exhaustive handler /
  `cannot assign to immutable binding` (実測 3 種とも file 名のみ)。
  checker の `Array::push(errors, ..)` 127 箇所中 offset を通すのは 45
  (code-read)。残りは first-occurrence テキスト探索で「もっともらしい別の行」を
  指しうる
- **`argument type mismatch for println: receiver type Int`** — 引数の話なのに
  "receiver"、期待型を言わない。頻出 (println は String 専用なので Int を
  渡す度に出る)
- **診断行のフォーマット不統一** (実測): `file: line L:C: msg` の行と
  `line L:C: msg` (file 無し) の行が同じ check 出力に混在する。行指向 grep を
  第一読者にする方針 (CLAUDE.md) に対する回帰
- `handle .. with A + B` は `expected { but got +` (nest せよの hint なし)
- ADR 番号・"replay engine" (存在しない pass 名)・`追記34` が英語メッセージに
  混入するクラスが effect 系に残存 (code-read: `inline_direct_perform.vibe:3445,
  11081` ほか)。適格性エラーは最初の 1 件しか報告されない
  (`file_compile.vibe:487`)

また S7 の hint (「`with Ask::Get` を main に足せ」) は従うと実行時クラッシュに
なる — hint が entry で放電不能な effect を区別していない。

## N9. 「measured, not folklore」の劣化 — 落とし穴節自体が folklore 化している

cheatsheet 落とし穴節の 2 項目が実装の進行で**逆方向に**古くなっていた (実測):

- `x?` optional 引数: 「パーサが受理するだけで semantics 未実装 (#1500)。省略で
  arity mismatch、body 内は T 束縛」→ 現行は**完全に実装済み** (省略で `None`、
  供給で `Some` 包装、body 内 `Option[T]`)。ドキュメントの他 2 箇所 (§optional
  引数、spec) は正しいので、**最も信頼されるべき節だけが誤っている**
- capability builtin の arity/型未検査 (#1513): `Stdout::write_stream(42)` /
  `()` とも現行は located error (実測)。節ごと古い

落とし穴節は「実測した日付/commit」を持たないので、close された issue の節が
残留しても検出機構が無い。**提案**: 各落とし穴に `(measured: <commit>)` を
付け、issue close 時に該当節を削る運用をルール化する。ほかの doc rot:
`docs/guide/when-to-use-effects.md:175-188` (削除済み構文 2 つを推奨パターンと
して掲載 — guide/ は doctest 対象外)、`docs/language-tour/effects.vibe.md:109-123`
(replay 意味論の記述と r4 反証済みの誤り、コメント内なので doctest 素通り)、
CLAUDE.md:405 (存在しない `src/tests/...mbt` への参照)、
`docs/spec/iterable-touch-points.md` (全編集手順が退役 MoonBit パス)。

## N10 (minor). その他の実測小物

- `is` の意味が位置依存: `if x is Some(v)` は束縛、`ready && x is Some(v)` は
  Bool 化して **v が束縛されない** (実測: `unknown name: v`)、
  `if x is Some(v) && ready` は parse error で書けない。spec の優先順位表に
  `is` の行が無い
- `test myname` (文字列なし) は located error で正しく拒否 (#1506 の修正は生き
  ている)
- 3 綴りの throw が全部通る: `throw(x)` / `perform Exception::Throw(x)` /
  `perform Error::Throw(x)` (実測)。`Error` は row と handle 位置では retire
  済みなのに perform 位置だけ生存 — 「1 概念 1 綴り」の残債
- `String::length("あい")` = 6、`s[0]` = 227 — ADR-0098 どおりの byte 意味論
  (正直)。ただし `string_head` 等は境界検査なしで不正 UTF-8 を黙って作る。
  そして spec/cheatsheet が「Unicode 系 API は無い」と書く一方で
  `String::utf8_length`/`utf16_length`/`unicode_length` が prelude から
  export されている (code-read)
