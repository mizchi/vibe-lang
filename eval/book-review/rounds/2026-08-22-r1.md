# book-review round 1 — 2026-08-22

Reader posture: new user, Rust/TypeScript background, reading
`book/en/` in SUMMARY order. Section 1 was written **before consulting
the implementation or the compiler**; section 2 measures the testable
items. Compiler: see the run log at the top of section 2.

## 1. Doc-only findings (no implementation consulted)

### D1. Two spellings for throwing, relationship never stated

Ch02 throws with `throw("divide by zero")`. Ch08 — the chapter that
*teaches* the failure effect — only ever writes
`perform Exception::Throw("...")`. Ch10 (`guard`) says the `else` must
leave "by `return` or by `throw(...)`". The book never says whether
`throw(...)` is sugar for `perform Exception::Throw(...)`, a builtin, or
a third thing — a direct hit on "one concept, one spelling" for the
language's flagship feature. Probe: p09.

### D2. `-1` is written `0 - 1` in some chapters and `-1` in others

Ch04 has `return -1`, ch02 has `Num(-3)`, ch13 passes `-1` as an
argument. But ch08 and ch10 both write `0 - 1` in match/handler arms
(`Throw(_) => 0 - 1`, `None => 0 - 1`). Either `-1` is fine in an arm
and those examples teach a superstition, or it is not fine and the book
hides a real pitfall. Probe: p01.

### D3. Ch03 says indexing gives "the code point"; ch05 says bytes

Ch03: "a character literal *is* its code point … Indexing a string
behaves the same way, so `s[0]` gives you a number." For ASCII the two
sentences agree; for anything else `'é'` (code point 233) and
`s[0]` of `"é"` (byte 195) are different numbers, and ch03's "behaves
the same way" is the wrong mental model that ch05 then has to undo.
Related: what `String::from_char_code` does above 127 — byte or code
point — decides whether ch03's "when you want the character back" recipe
round-trips non-ASCII. Probe: p02.

### D4. The interpolation chapter never interpolates a struct

Ch05 claims "your own types get \[a `to_string`\] from `derive (Show)`"
— but its example prints `Point::to_string(p)` explicitly, never
`\{p}`. Ch15 *does* interpolate an enum directly (`\{Color::Green}`).
If `\{p}` works, ch05 undersells it; if it does not, ch05's claim is
false. Probe: p03 (with Show), p04 (without — diagnostic quality;
ch05/ch20 claim missing Show is a compile error, #1445).

### D5. Ch03 teaches `__to_string`

The optional-arguments example builds its result with
`String::concat(name, String::concat(" x", __to_string(n)))`. A
double-underscore name looks internal (it is the desugar target
mentioned in CLAUDE.md), it is taught nowhere, and the same line could
have been interpolation — which the book has already introduced by then.
Reads as a leak from the implementation into the narrative.

### D6. Import-brace forms are inconsistent and unexplained

Ch11 shows importing functions (`{ triple }`, `{ f as renamed }`).
Ch13 writes `import @vibe/core { struct MutMap }` — a `struct` keyword
inside the braces, never remarked on. Ch15 imports a trait with no
keyword (`import @vibe/core { Default }`). What requires the keyword,
and for which declaration kinds, is stated nowhere in the book.
Probe: p05.

### D7. `.vibe` vs `.vibex` is never explained

Ch01 has you write `hello.vibex` and run `vibe check hello.vibex`;
`vibe new` writes `main.vibex`; every other chapter and every CLI
example uses `.vibe`. The book never says what the two extensions mean
or when each is required. (Doc gap; no probe — needs the CLI docs, not
a compile.)

### D8. Where does the `require … = #pkg:sha1:…` pin line live?

Ch11 shows the pin syntax in a bare `text` block. Ch01 said
dependencies go in `vibe.deps`, but ch11 never names the file the
`require` line is written in. A reader cannot reproduce "Reproducible
builds" from the book alone.

### D9. Ch17's example row is unexplained

`fn main with Console + Exception` — the chapter never says why
`Exception` is required (presumably `TaskHandle::join` can rethrow, but
that is a guess). The one chapter about effects-on-rows-in-practice
does not account for its own row.

### D10. Ch17's Send table vs `spawn` taking a closure

The table says closures "may not" cross a spawn — yet `spawn`'s second
argument *is* a closure. The intended distinction (the spawned body vs
values captured by it / sent through channels) is real but unstated,
and a careful reader hits the apparent contradiction immediately.

### D11. Ch09's sample diagnostic hints the deprecated spelling

The `with Stdout` mismatch example ends with
`hint: add 'with Console::write_stream + Stdout' to 'main'` — hinting a
*capability* into `with`, two paragraphs before the chapter explains
that in the split form a capability must be in `allows` (and the same
page calls `Stdout` an older label). If the compiler really says this,
the hint steers readers to the legacy spelling; either way the book
shows it without comment. Probe: p07 covers the neighboring case
(missing `Console` entirely).

### D12. Array indexing out of range: never mentioned

Ch13 teaches both `xs[0]` and `Array::get(xs, i)` (two spellings, no
comment on the difference, if any) and `MutMap::get` returning
`Option` — but what `Array::get(xs, 10)` on a 3-element array does is
said nowhere in the book. Trap, sentinel, or silent garbage — on the
project's own triage this is the P0-shaped question. Probe: p06.

### D13. "A top-level `fn` annotates its parameters and return type in full"

Ch15 states this as a rule, but `fn main with Console` (every chapter)
has no return annotation, and ch12's `fn double(n: Int) -> Int` next to
ch09's `-> Unit` leaves unclear whether `-> Unit`/`->` is optional in
general or `main` is special. Probe: p14.

### D14. Minor

- Ch06 asserts the non-escaping `let mut` lives "in a machine
  register" — an implementation claim a reader cannot check, sitting in
  a beginner chapter (wasm has no registers; presumably "a wasm local").
- Ch05 introduces `Float` (`1.5f`) in two sentences; `Float` never
  appears again. No arithmetic/mixing rules anywhere.
- Ch04's pipe-`_` vs section-`_` disambiguation rule ("bare `_` is the
  pipe slot, `_` inside a larger expression is a lambda") never says
  what a bare `_` argument means *outside* a pipe. Probe: p12.
- Ch08/ch20's `handle` eligibility examples differ (ch08's rejected
  shape has the perform *inside* the argument to the opaque call;
  ch20's has it too — but ch20 says giving the *literal* `with Ask`
  repairs it while ch08 says give "the binding or parameter" a row;
  same diagnostic text quoted in both). Consistent enough, but the two
  quote the identical diagnostic for slightly different programs —
  worth re-measuring whenever the text changes (existing fixtures cover
  this; no new probe).
- SUMMARY.md's Japanese list has no entry for the appendix
  (`99_appendix.md`), so the ja sidebar ends at ch20. Deliberate?
- Ch12 shows failure output naming only `assert_eq failed` with
  expected/actual but no file:line; if that is the real output, a
  multi-assert test does not say *which* assert fired (the test name,
  yes; the line, no). Probe: p15.

### M1. Book fixes the measurements ask for (doc side)

- **D2 resolved (p01):** `-1` is fine in a match arm. Ch08/ch10's
  `0 - 1` is a superstition the book invented; rewrite those arms as
  `-1` (with a doctest run proving it).
- **D3 confirmed (p02):** `"é"` has `len = 2`, `s[0] = 195` — bytes,
  as ch05 says; ch03's "indexing … behaves the same way \[as the code
  point\]" is false for non-ASCII and should be rephrased byte-first.
- **D4 resolved (p03):** `\{p}` works with `derive (Show)`. Ch05's
  example should interpolate the struct directly instead of calling
  `Point::to_string(p)` — the current example undercuts the claim it
  illustrates.
- **D1 resolved (p09):** `throw("m")` and
  `perform Exception::Throw("m")` are the same operation and one
  handler catches both. The book should say so, once, in ch08.
- **D6 resolved (p05):** the `struct` keyword in an import brace is
  optional — plain `{ MutMap }` imports the type and activates
  `MutMap::*`. Two spellings for one concept, used inconsistently
  across ch13/ch15 and `docs/adding-modules.md` (which still implies
  the keyword is what "activates the namespace"). Decide the canonical
  form; teach one.
- **D13 refined (p14/p16):** the return annotation is mandatory for
  every top-level `fn` — a `with` row does not lift that — **except
  `main`**. No chapter says `main` is special; ch15's "in full" rule is
  wrong by omission.
- **D12 answered (p06):** out-of-range `Array::get` traps. The book
  never says so; ch13 should (it is the difference between "honest
  crash" and the reader assuming a sentinel).

### M2. Compiler findings (issue candidates)

1. **Missing-row hint teaches the legacy label (p07).** For a bare
   `println`, the error and hint say `Stdout` — the label the book,
   the cheatsheet (#2102/#2117) and ch09 all call legacy, and which
   authorizes *less* than `Console`. A beginner following the very
   first chapter's "delete `with Console`" experiment is steered to a
   spelling the docs tell them not to use. The row machinery
   presumably reports the internal lowering label; the hint should
   render the current surface name.
2. **Type errors without positions, two more instances (p04, p11).**
   The interpolation-needs-Show rejection carries no position *and no
   file*; the if-branch mismatch carries the file but no line. Both
   are #1567's shape (checker anchors exist, literals have no offset
   slot). Non-exhaustive match (p08) also names no position — for the
   book's "the errors point at every match that now has a hole" to be
   true, it needs one.
3. **`Array::get` OOB is a bare `unreachable` (p06).** Honest but
   hostile: the user sees `[crash debug] heap_ptr=…` and a wasm stack,
   with nothing naming the array, the index, or even "index out of
   bounds". Compare `MutMap::get` returning `Option`. At minimum the
   trap should say what trapped; the book should document the
   behavior either way.
4. **`if condition must be Bool` never says what it got (p10).** With
   `flag?: Bool` the actual type is `Option[Bool]` and the fix (match
   on `Some`/`None`) is exactly what ch03 teaches — the diagnostic
   names neither. Adding "got `Option[Bool]`" would carry the repair.
5. **`unknown name: _` (p12).** `_` has two documented meanings (pipe
   slot, lambda section) and this message admits neither exists here.
   "A bare `_` is only meaningful as a pipe slot or lambda-section
   argument" would turn a shrug into an answer.
6. **Assert failures have no location and a trailing trap (p15).**
   The report names the test and expected/actual but not the line, so
   two identical asserts in one test are indistinguishable; and after
   the tidy report the runner prints
   `trap: RuntimeError: unreachable`, which reads as a second,
   scarier failure but is just the assert's implementation.
7. **Exemplary diagnostics worth imitating (p13, p17, p18).** The
   `continue`-arity message (#1284) and the reserved-word pair are the
   house style at its best: located, the edit named, the neighboring
   misconception (`break` asymmetry, `r#`) pre-empted. They are what
   findings 2, 4 and 5 should be graded against.
