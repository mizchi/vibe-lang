### R2-2. Where the `require … = #pkg:sha1:` pin lives (D8)

The two docs do not actually disagree — they describe two different
lanes, and the launcher's own `pkg)` comment states the split:
`vibe add/fetch/verify` is the `vibe.deps`/`vibe.lock` **URL vendoring
lane** (docs/cli-commands.md), while `require … = #pkg:sha1:` is the
**content-addressed registry lane** (docs/module-system-v2.md §6,
`vibe pkg`). The pin line is a header directive read by
`extract_require_pins` in the contract loader; in practice it lives at
the top of `index.vpkg`.

Measured how far a require head is accepted outside the contract, and
the lanes disagree (stage2; the `.vibe` rows are p31, the `.vibex`
rows p35 -- both pinned by the harness):

| file | lane | result |
|---|---|---|
| `.vibe` + require head | FS build (`_start`) | **compiles and runs** |
| `.vibe` + require head | `vibe check` | `error: line 1:29: unexpected token: =` |
| `.vibex` + require head | `vibe run` / FS build | `error: unknown # directive: pkg` |
| `.vibex` + require head | `vibe check` | `unexpected token: =` |

The first two rows are the finding: `vibe check` — the verb the book and
CLAUDE.md name as the authority on "does this compile" — reports a parse
error for a file the build lane accepts (the early gate's 6c writes
exactly this shape and expects it to build). Issue filed (M2-1). Book
fix: ch11 now names `index.vpkg` as the pin's home and separates the two
lanes in one parenthetical; ch01 says what `vibe.deps` actually holds.

## 2. New findings from the fresh pass

### R2-6. Ch18's `type-at` example answered for the wrong symbol

Book claimed `vibe type-at hello.vibe 5 4` prints `(Int, Int) -> Int`
"on the name add" — measured (p25): 5:4 sits on `main` and prints
`() -> () with Console`. `1 4` (and `6 14`, the call site) answer

`symbols` output (`add 12 3 6`) and state the empty-output convention
for a no-identifier position.

### R2-7. Two `vibe test` reporters (p26)

The book's ch12 console blocks match `scripts/vibe_test.sh` exactly
(`ok   <file>` … `[vibe-test] 1 passed, 0 failed (1 files, 1 tests)`;
FAIL block in the quoted order; no trailing trap — the round-1 p15 noise
is gone from this lane). But the **launcher's** `vibe test` — what an
installed user runs — prints a different format: `ok:   <file>` (colon),
no `[vibe-test]` summary line at all, and on failure the `assert_eq`
block comes *before* the `FAIL:` line. Issue filed (M2-2); the book
keeps the script format, which that issue proposes as the single
reporter.
