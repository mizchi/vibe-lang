### R2-2. Where the `require … = #pkg:sha1:` pin lives (D8)

The two docs do not actually disagree — they describe two different
lanes, and the launcher's own `pkg)` comment states the split:
`vibe add/fetch/verify` is the `vibe.deps`/`vibe.lock` **URL vendoring
lane** (docs/cli-commands.md), while `require … = #pkg:sha1:` is the
**content-addressed registry lane** (docs/module-system-v2.md §6,
`vibe pkg`). The pin line is a header directive read by
`extract_require_pins` in the contract loader; in practice it lives at
the top of `index.vpkg`.

Measured how far a require head is accepted outside the contract, and
the lanes disagree (stage2; the `.vibe` rows are p31, the `.vibex`
rows p35 -- both pinned by the harness):

| file | lane | result |
|---|---|---|
| `.vibe` + require head | FS build (`_start`) | **compiles and runs** |
| `.vibe` + require head | `vibe check` | `error: line 12:26: unexpected token: =` |
| `.vibex` + require head | `vibe run` / FS build | `error: unknown # directive: pkg` |
| `.vibex` + require head | `vibe check` | `error: line 12:26: unexpected token: =` |

The first two rows are the finding: `vibe check` — the verb the book and
CLAUDE.md name as the authority on "does this compile" — reports a parse
error for a file the build lane accepts (the early gate's 6c writes
exactly this shape and expects it to build). Issue filed (M2-1). Book
fix: ch11 now names `index.vpkg` as the pin's home and separates the two
lanes in one parenthetical; ch01 says what `vibe.deps` actually holds.

(The table is this round's measurement. #2227 was fixed the same day —
check's pre-parse and the `.vibex` entry validation now blank the pin
head like every build-lane ingestion, and probes p31/p35 pin all lanes
agreeing.)

### R2-4. `String::from_byte` (from_char_code) — alias landed, book updated

`String::from_byte` resolves and runs on both seed and stage2 (p23);
`core/builtin_name.vibe` canonicalizes it and marks `from_char_code`
deprecated with hint "use String::from_byte". This round recorded "no
deprecation warning fires from `vibe check`" (p23: exit 0, no output) —
**that claim was a measurement artifact of the probe's shape**: a bare
`String::from_char_code(65)` statement warned all along
(`warning: line N:col M: 'String::from_char_code' is deprecated: use
String::from_byte`, stderr, exit 0), and p23 got silence only because
the deprecated-use scan skipped names inside string interpolations —
which is exactly the shape ch03/ch05 recommend. That interpolation
blind spot was the real #2203 remainder and is fixed (the scan re-lexes
each `\{...}` snippet, positions shifted back to file coordinates);
p23's directive now pins the warning. Ch03/ch05 (en+ja) lead with
`from_byte` and call `from_char_code` the older name. The raw-byte
contract above 0x7F is unchanged; bounds are now measured and in the
cheatsheet: always 1 byte, low 8 bits, no trap (`256` → byte 0, `-1` →
byte 255, `1000` → byte 232).
