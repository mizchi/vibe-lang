# Compiler OUTPUT size baseline — compiled wasm bytes for each
# bench/binary_size/*.vibe sample, measured by scripts/size_ratchet.sh
# against a stage2 built from the same commit.
#
# WHY THESE AND NOT THE COMPILER'S OWN SIZE (#1109-4): these are the sizes
# the compiler PRODUCES, so a codegen regression here makes every user
# program bigger. The compiler's own artifacts (stage2.wasm, the committed
# bundles, the flat module source) legitimately grow whenever a feature
# lands — ADR-0076 追記34 V2 alone added ~2.4% — so ratcheting those would
# fight ordinary development instead of protecting anything. The perf
# report still tracks them; they just are not gated.
#
# Byte-deterministic for a fixed (stage2, sample) pair, so this can block
# CI without flakes. Threshold = committed baseline + 2% per sample (tight:
# these numbers move only when codegen itself changes).
#
# Rebaseline when an intentional codegen change moves a number (either
# direction — ratchet DOWN after a size win so the gate protects it):
#   bash scripts/generations.sh build --out-dir /tmp/size_gen
#   bash scripts/size_ratchet.sh /tmp/size_gen/stage2.wasm --print
#   # -> copy the reported lines over the table below
# and commit the new numbers with the codegen change, noting old -> new
# (and why) in the PR.
#
# Format: comments/blank lines ignored; remaining lines are "<name> <bytes>".
#
# 2026-07-26 initial baseline (#1109-4), measured on main 458170fc + the
# #1114 capture fix. Locks in the #1107 Phase 1-4 wins (ADR-0077 release
# strip, funcref table minimization) that were previously unprotected.
#
# 2026-07-28 rebaseline: Map[String,V] open-addressing read index (PR #1191)
# registers 5 new runtime builtins (hash / capacity-for-count / index-insert
# / build-index / probe-index, codegen/builtin_bodies/bodies_core_b.vibe).
# Like every other static builtin (eq, str_eq, arr_new, ...) these are
# unconditionally part of the linked module's fixed runtime footprint --
# there's no usage-based tree-shaking for builtins today, only for top-level
# user statements (core/dce.vibe) -- so every sample grows by a small fixed
# amount even though none of these five samples touch Map. closure_indirect
# 2657->2682, fib 755->780, fizzbuzz 1333->1358, hello_world 791->816,
# variant_float 5303->5636 (the largest sample eats the biggest absolute
# delta from the new function bodies, hence the largest %).
#
# 2026-07-31 rebaseline (#1262 / PR #1274, ADR-0092 allocator work):
# vibe_rc_drop grew 432->646 B (size-bin free pushes at its two free
# sites) and vibe_rc_alloc 190->285 B (bin-first pop + bounded 16-node
# walk) -- a CONSTANT runtime-builtin delta for every RC output that
# links them, verified byte-exact against a main-built stage2 (every
# user function identical; the whole diff is those two builtins). Bought:
# RC selfcompile ratio 3.86x -> 1.97x (unbounded O(list) exact-fit walk
# was 44% of compile CPU). closure_indirect 2682->2991 (its live set
# includes both builtins), variant_float 5636->5657, fib/fizzbuzz/
# hello_world unchanged (rc builtins stubbed out of their live sets).
#
# 2026-08-01 rebaseline (#1262 / PR #1282, borrowed-arg0 ABI enabled by
# default): closure_indirect 2991->3135 (+144 B, +4.8%), variant_float
# 5657->5643 (-14 B), fib/fizzbuzz/hello_world unchanged. The ABI's
# per-use-paired planner accounting does not only remove dup/drop pairs:
# a view-call binding holds no initial owned reference, so its last owned
# use now DUPS where it previously did not (its scope-end drop is
# suppressed in exchange). closure_indirect is the sample whose live set
# carries that shape; variant_float nets out slightly smaller. Bought:
# selfcompile RC ratio 1.951 -> 1.659, and gate section 40d heap_used
# 1,920,352 B -> 424 B at N=20000. NOT attributed function-by-function --
# the numbers reproduce byte-exactly against a stage2 built from this
# branch, and main is green at the old numbers, so the delta is this
# change; if the author reads the growth as unintended, revert this entry
# rather than widen the tolerance.
#
# 2026-08-15 rebaseline (#1666, derive-generated code now faces DCE): the
# whole-program DCE pass moved from before `desugar_trait_dicts` to after it
# (codegen/wasi/linked_compile.vibe), so the `T::equals` / `to_string` /
# `compare` / `default` bodies that `desugar_derives` synthesizes per enum
# and struct are now subject to reachability instead of being emitted
# unconditionally. Attribution measured A/B against a stage2 built from
# main@42156b0d8 in the same environment:
#   sample            committed  main   this branch   this change's delta
#   closure_indirect  3135       2456   2456          0
#   fib               780        795    795           0
#   fizzbuzz          1358       1384   1384          0
#   hello_world       816        831    831           0
#   variant_float     5643       4459   4089          -370  (-8.3%)
# i.e. FOUR of the five moves below are MAIN'S OWN drift accumulated since
# the previous rebaseline (already reflected in the "main" column before
# this branch existed); only variant_float -- the one sample that declares
# an enum -- moves from this change, and it moves DOWN. Ratcheted to the
# measured values per the header policy so the gate protects the win.
# Isolated control: a 5-variant enum no user code touches cost 784 B of
# output before this change (1445 B vs 661 B for the same program without
# it) and costs 0 B after (661 B vs 661 B).
#
# THIS ROW IS #1666'S REGRESSION GUARD. variant_float is the only sample that
# declares an enum, so it is the only one whose bytes move when
# derive-generated code stops facing DCE -- and 4459 is +9.0% over the 4089
# below, well past this file's +2% tolerance. A compiler_gate.sh section that
# asserted the same property directly was tried and removed: the gate compiles
# through the raw 3-arg `cli_main` ABI under `VIBE_RC=0`, which routes to
# `compile_wasi_module_no_dce_impl` -- the one lane `enable_late_dce = false`
# deliberately exempts -- so it demanded pruning from the lane that contracts
# not to prune. Measured on one stage2, varying only VIBE_RC: `VIBE_RC=0` gives
# 1264/638 (no pruning, by design), VIBE_RC unset gives 661/661. The row below
# tests the lane that actually ships.
#
# 2026-08-22 rebaseline (#2199, PR #2220): the Array::get / Array::set OOB
# abort now prints a static message naming the operation before its
# `unreachable` (a bare trap read as a compiler bug). Every linear-lane
# module carries the two message strings (64 B of data) plus the
# i64.const + call prefix in the two builtin bodies -- the same
# unconditional-runtime-footprint shape as the #1191 note above, so every
# sample grows by a small fixed amount (~86-95 B) even though none of them
# indexes out of range. Fuel and B/op are unchanged: the happy path
# executes nothing new. closure_indirect 2456->2542, fib 795->881,
# fizzbuzz 1384->1470, hello_world 831->917, variant_float 4089->4184.
#
# 2026-08-22 rebaseline 2 (#2199 ask 2): the OOB abort now reports the
# index and length (`Array::get: index 10 out of bounds for length 3`) via
# two new always-linked runtime builtins -- __rt_print_i64_raw (decimal
# printer without the trailing newline) and __rt_oob_abort (assembles
# prefix + idx + " out of bounds for length " + len) -- and the same
# formatted abort now also covers Bytes::get / Bytes::set /
# String::byte_at, which previously trapped bare. Same
# unconditional-runtime-footprint shape as above: +99 B fixed on four
# samples (the two new bodies + message fragments + per-site value pushes,
# minus the two retired static message strings); variant_float pays +289
# because the two extra function indices push more of its call sites past
# the 1-byte LEB boundary. Happy path unchanged. A/B against a stage2
# built from the pre-change commit reproduces the previous row exactly, so
# the whole delta is this change. closure_indirect 2542->2641, fib
# 881->980, fizzbuzz 1470->1569, hello_world 917->1016, variant_float
# 4184->4473.
#
# 2026-08-27 rebaseline (#2344, PR #2358): Int::popcount / Int::ctz /
# Int::clz land as registry builtins, and like every other static builtin
# they are part of the linked module's fixed runtime footprint -- the same
# unconditional shape as the #1191 and #2199 notes above. +20 B on ALL FIVE
# samples, exactly, even though none of them counts a bit: three bodies of a
# handful of instructions each, plus their func-table and type entries. Fuel
# and B/op are unchanged (the happy path executes nothing new) and the
# compiler's own artifacts move DOWN in the same PR (#2342 retires the V128
# intrinsics: stage2.wasm -0.12%). Reproduced byte-exactly against a stage2
# built from this branch, matching CI's numbers to the byte.
# closure_indirect 2641->2661, fib 980->1000, fizzbuzz 1569->1589,
# hello_world 1016->1036, variant_float 4473->4493.
#
# NOTE the trend this row makes visible: fib has gone 755 -> 780 -> 795 ->
# 881 -> 980 -> 1000 across the rebaselines above, +32% since the initial
# baseline. Of those five steps, FOUR are attributed by their own entries to
# builtins linked unconditionally that the sample never calls -- #1191 (+25),
# #2199 (+86), #2199 ask 2 (+99) and this one (+20), 230 of the 245 bytes.
# The remaining step (780 -> 795) is main's drift, recorded but not
# attributed, by #1666's own table. Each of those entries says the same
# thing: "no usage-based tree-shaking for builtins today, only for top-level
# user statements (core/dce.vibe)". Tracked as its own issue rather than
# widened tolerances here.

# 2026-08-28 rebaseline (#2345 / PR #2372): four Bytes search builtins --
# index_of_bytes, index_of, count, last_index_of. closure_indirect
# 2661->2681, fib 1000->1020, fizzbuzz 1589->1609, hello_world 1036->1056,
# variant_float 4493->4513. EXACTLY +20 B on every sample, which is the
# interesting part.
#
# The entries above all say builtins have "no usage-based tree-shaking today"
# and so land whole in every module. MEASURED, that is no longer true of the
# linear lane. Four bodies of 100+ B each would be +400..800 B, not +20; and
# the compiled fib.wasm contains ZERO 0xFD bytes -- not one SIMD instruction,
# so not one of the four bodies is in it. The +20 is per-builtin table
# overhead, ~5 B each. Whatever those older entries were describing, the
# thing to write down now is the measurement, not the inherited explanation.
#
# This rebaseline is not optional bookkeeping: before it, every sample sat at
# EXACTLY the +2% limit (fib 1020 against a 1020 ceiling). The gate passed and
# had zero headroom left, so the next codegen change of any kind would have
# failed it for reasons that had nothing to do with that change.
#
# The wasm-gc lane is the opposite and is NOT gated here: it links builtins
# unconditionally, so these four cost it +2.2..3.1% on every perf scenario
# including programs that never search bytes. That is #2359, not this file.
