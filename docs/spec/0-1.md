# vibe 0.1.0 — release specification

> **Normative for the `0.1.0` release.** This document is *pinned*: it
> describes one version and does not track `main`. Every other document in this
> repository is *living* — it describes whatever the tree currently builds.
> When the two disagree about 0.1.0, this one is right about 0.1.0 and the
> other is right about now.

0.1.0 is **the first release usable by anyone but the author** (ADR-0109). The
only previously published version is `v0.0.1` (2026-04-14), built by a MoonBit
host implementation that no longer exists. Between them the language was
rewritten in itself, so 0.1.0 is not an increment on `v0.0.1` — it is a
different compiler that happens to share the name.

---

## 1. What this document is, and what it deliberately is not

This specification **states identity, boundaries and conformance. It restates
no definition that a living document already owns.**

That restraint is the whole design. This repository has deleted a document for
violating it: `docs/language-tour/` was a fourth surface beside the cheatsheet,
the tutorial and `syntax.md`, and it rotted exactly as predicted — doctest
compile-checks fenced code and is blind to prose, so the tour went on calling
`String` a UTF-16 string long after ADR-0098 made it a byte string, and calling
`index.vibei` the package boundary long after `index.vpkg` became it. Nothing
caught either. A fifth surface that paraphrased the grammar would fail the same
way, and it would fail *as the release specification*, which is worse.

So the rule here is mechanical:

| question | answered by |
| --- | --- |
| What does this syntax mean? | [cheatsheet.md](../user/reference/cheatsheet.md), [syntax.md](../user/reference/syntax.md) |
| What is promised under SemVer? | [stable-surface.md](../user/reference/stable-surface.md) |
| Why is it this way? | [adr.md](../internal/design/adr.md), [decisions.md](../internal/design/decisions.md) |
| What changed since `v0.0.1`? | [release-notes-0.1.0.md](../user/getting-started/release-notes-0.1.0.md) |
| How do I learn it? | `book/en/` |
| **What IS 0.1.0, exactly?** | **this document** |

Everything below is either a version-pinned fact (an artifact, an identity, a
boundary) or a cross-cutting invariant that no single document owns. Where a
section could be mistaken for a definition, it cites the owner.

## 2. Identity

| | |
| --- | --- |
| Version | `0.1.0` |
| Tag | `v0.1.0` |
| Ladder position | first release usable by anyone but the author (ADR-0109) |
| Predecessor | `v0.0.1` (2026-04-14), MoonBit-host era |
| SemVer regime | 0.x — breaking change to the stable surface is a **Minor**, compatible change a **Patch** ([stable-surface.md §1](../user/reference/stable-surface.md)) |
| License | Apache-2.0 |
| Implementation | self-hosted; the compiler is written in vibe and built from a pinned seed |

`vibe version` reports the SemVer reference point, and
`scripts/build_release_assets.sh` refuses to build assets whose version
disagrees with the tag, so what a toolchain reports is what it was published
as.

**The candidate line is `0.1.0-rc.2`.** This document describes 0.1.0; an rc is
a candidate *for* it, carrying the same content under a number that says nobody
has finished hunting for its bugs yet. The two are not interchangeable: an rc
is published as a GitHub pre-release, so it is not what the README's installer
resolves to, and what promotes one to the release is a bug hunt rather than
more features
([release-roadmap.md](../internal/project/release-roadmap.md#what-promotes-an-rc-to-the-release)).
A pre-release reduces to the release it documents wherever the tree checks a
version, so `0.1.0-rc.2` is checked against the 0.1.0 notes and this
specification. `0.1.0-rc.1` came before it and published cleanly; the line
moved because this tree is no longer the one that candidate names.

## 3. What constitutes the release

0.1.0 is a set of published artifacts, not a source tree. An installation is
0.1.0 if and only if it was materialized from these.

### 3.1 Release assets

Published under the `v0.1.0` tag by `.github/workflows/release.yml`, which is
triggered by the tag push alone:

| asset | what it is |
| --- | --- |
| `vibe-compiler-v0.1.0.wasm` | the compiler, as a wasm module |
| `vibe-compiler-module-source-v0.1.0.vibe` | the flat compiler module source it was built from |
| `vibe-compiler-seed-v0.1.0.json` | the seed manifest the build bootstrapped from |
| `vibe-toolchain-v0.1.0.tar.gz` | the platform-independent toolchain: the launcher, the pkg and warm-pool scripts, the LSP scripts, the context pack, the shipped stdlib packages, and `stdlib-hashes.tsv` |
| `viberun-v0.1.0-<target>.tar.gz` | one prebuilt runner per target |
| `release-manifest.json` | every asset with its sha256, the runner per target, the embedded wasmtime version |
| `SHA256SUMS.txt` | checksums over the above |

### 3.2 Runner targets

| target | note |
| --- | --- |
| `x86_64-unknown-linux-gnu` | |
| `aarch64-unknown-linux-gnu` | |
| `aarch64-apple-darwin` | |
| `x86_64-apple-darwin` | best-effort — its build job is `continue-on-error` while GitHub still hosts an Intel macOS runner |

A target whose tarball is absent is **recorded as absent** rather than
silently substituted: `build_release_assets.sh` writes no runner row for it,
and `vibe self update` then refuses that host by name. There is no fallback
runner.

### 3.3 Bootstrap seed

The compiler is built from a committed, sha256-pinned seed rather than from
itself. 0.1.0's seed is recorded in `bootstrap/seed.json` at the tagged commit
and is reproducible two ways: from its published `seed/*` release, or — if that
release is unavailable — by rebuilding from the manifest's `source_commit`,
which must hash to the same artifact. `scripts/ensure_seed.sh` does both and
verifies the result either way.

### 3.4 Shipped packages

Six packages ship inside the toolchain bundle: `@vibe/core`, `@vibe/ast`,
`@vibe/parser`, `@vibe/builtin`, `@vibe/console`, `@vibe/wit_runtime`. Their
BLAKE3 package hashes are computed **by the compiler this release ships** and
recorded in `stdlib-hashes.tsv` inside the bundle. The other `@vibe/*` and
`@vibex/*` packages in the repository are the compiler's own dependencies and
are not part of an install.

## 4. Conformance

These are the checks that answer "is this really 0.1.0", in the order that
makes a failure cheapest to diagnose.

1. **`vibe version` reports `0.1.0`** — exactly that, with no suffix. A
   suffix means something other than the release: `-dev` a checkout,
   `-rc.N` a candidate that has not cleared the bug hunt.
2. **Every asset hashes to its row** in `release-manifest.json`, and
   `SHA256SUMS.txt` verifies over the downloaded bytes. `install/install.sh`
   and `vibe self update` perform this before moving anything into
   `toolchains/`; a mismatch refuses the install and leaves the previous
   toolchain in place.
3. **The install carries no checkout.** A conforming installation compiles and
   runs a program with no repository `lib/`, no `_build/`, and no
   checkout-local seed on its search path.
4. **`vibe check` is the verdict.** Empty output and exit 0 means clean; any
   diagnostic means exit 1. This holds on both the filesystem lane and
   `--single-file`, and `--json` returns the same LSP `Diagnostic` array on
   both, byte-identically.
5. **The stable surface resolves.** Every symbol
   [stable-surface.md §3](../user/reference/stable-surface.md) lists as frozen
   is reachable at the spelling given there.

## 5. The language at 0.1.0

The definitions are the cheatsheet's and `syntax.md`'s; the SemVer promise is
`stable-surface.md` §2. What follows is only what no single document owns:
the invariants that cut across all of them, and which a reader has to know
before the individual definitions mean what they appear to mean.

### 5.1 The failure ordering

This is the design rule the rest of the language is derived from, and it is
normative:

> **Never be silently wrong** > honesty of representation > pleasantness of
> the surface syntax.

It is not a slogan. It is why triage ranks a silent wrong answer (P0) above a
crash (P1), and it is why several constructs below **refuse to compile** in
cases where a more permissive language would answer. Where 0.1.0 declines to
answer, that is the specification, not an omission.

### 5.2 Equality is structural or refused — never reference identity

`==` compares by content. At a concrete type this covers arrays, tuples,
structs and their nestings, through a name, through a function's return value,
through a parameterized type alias, and through a generic struct or enum at
each concrete instantiation. A generic `[T: Eq]` bound compares by content too:
`Eq` carries `equals(Self, Self) -> Bool` and `derive (Eq)` registers the impl,
so a bounded `==` answers exactly like the concrete one.

What the compiler cannot classify is **refused at build time**, with a message
naming the edit — not answered by length, not answered by identity, and (since
#2475) not a bare runtime trap on a program that compiled clean. The refusal
lands on `vibe build` / `vibe run` / `vibe test`; `vibe check` does not run
that pass.

`Ord` is still a marker trait, so a `[T: Ord]` bound at an aggregate is
refused: it would dispatch to a builtin `<` that reads the box rather than the
value, which is wrong in both directions at once. A formal with no `Eq` bound
is refused the same way.

**There is no silent reference equality anywhere on this surface.** Every lane
either answers correctly or refuses. That sentence is the contract; the
per-shape detail is the cheatsheet's.

### 5.3 An aggregate is shared, never copied

`Array`, `Bytes`, a `struct` and an `enum` payload are handles. Binding one to
a second name, passing it to a function, storing it in another aggregate, or
capturing it in a closure all give the same object, and a mutation through any
of them is visible through all of them. There is no implicit copy and no syntax
that asks for one — **a copy is always an explicit call** (`Array::slice`).

A `String` is immutable, so its sharing is unobservable.

0.1.0 ships **no borrow syntax, no lifetime annotation and no module-level
`Ref`/cell**. Those are withdrawn rather than deferred, on measurement — see
§7.

### 5.4 Effects and capabilities ride the row

Functions are pure by default and declare what they do with `with E`. An entry
point **grants** with `allows`; a called function **requires** with `with`.
Authority is settled once, in the earliest phase of build → apply →
instantiate, and does not change during a run.

The consequence a user sees: a call site stays an ordinary function call. There
is no capability object to thread, and no monadic wrapper around a return
value.

### 5.5 Representations are what the memory is

- An `Int` is 63-bit, tagged, and **wraps as 63-bit two's complement on every
  backend** — the same values everywhere. Literals up to 2^62-1.
- A `String` is a **byte** string, indexed by byte offset.
- Every source position the CLI reports or accepts is a **byte** position. The
  sole documented exception is the LSP boundary (`--json`, `vibe lsp`), which
  converts to 0-based lines and UTF-16 code units. The contract and its known
  deviations are [source-range-contract.md](../user/reference/source-range-contract.md).

### 5.6 The package boundary is the contract file

`index.vpkg` is the package contract and the public API boundary (ADR-0070).
Importing a file inside a package boundary is a compile error. `index.vibe` is
a facade, not a boundary; `index.vibei` is legacy and no longer exists in this
repository.

Dependencies are distributed over git with no central registry, pinned by
content hash in the root `index.vpkg`. **There is no lock file — the `require`
line is the lock.**

## 6. The toolchain at 0.1.0

### 6.1 The frozen command surface

The frozen subcommands and their contracts are
[stable-surface.md §4](../user/reference/stable-surface.md); the full flag
reference is [cli-commands.md](../user/reference/cli-commands.md). Two
properties of the whole surface are specified here because they belong to no
single command:

**The CLI's first intended reader is an LLM, not a person.** That is a design
constraint with testable consequences, and they are part of the release:

- one finding per line, fixed field order — greppable without a parser;
- **empty output means clean**, so "no problems" is decidable from the output's
  existence;
- a diagnostic names **the edit that fixes it**, not an internal pass name or
  an ADR number;
- a question the CLI cannot answer is a gap in the CLI, not a caller's
  technique.

**One verb per question.** `vibe check` is the single verb for "does this
compile"; `--single-file` is a mode of it, for unsaved editor buffers, and
`vibe diagnostics` is deprecated and frozen for existing editors.

### 6.2 Backends

The **linear-memory backend is the stable surface**. The wasm-gc backend is
opt-in (`VIBE_BACKEND=gc` and friends) and experimental.

Generated wasm declares the feature level it requires, and `--allow-*`
const-folds and DCEs away the code for capabilities that were not granted. The
levels and how they are tracked are [feature-levels.md](../user/reference/feature-levels.md).

The compiler's own execution base and the wasm it generates are held to
different standards on purpose: the runner may depend on flagged proposals,
the generated module may not.

### 6.3 Host boundary

What may cross the host boundary, and in what representation, is
[host-abi.md](../user/reference/host-abi.md). The synchronous host runtime
execution contract is settled (#1346).

## 7. What 0.1.0 does not include

A release specification is as much about the edges as the contents. These are
**not** in 0.1.0, and the distinction between the two lists matters.

### 7.1 Outside the SemVer promise, but present

Enumerated in [stable-surface.md §6](../user/reference/stable-surface.md). It
can break within a Minor. The load-bearing members:

- **The suspendable-task lane** — `TaskGroup::spawn_suspend`, `pump_all`,
  `sleep_wait`, `send_wait` / `recv_wait`, in `@vibe/concurrent/experimental`.
  `import @vibe/concurrent/experimental` is **rejected by `vibe check` and by
  `vibe build`** unless `VIBE_UNSTABLE=1` — an error, not a warning, and the
  same answer from both verbs. The structured-concurrency core it extends
  (`@vibe/concurrent`: `TaskGroup`, `TaskHandle`, channels, `Parallel::map`,
  the `Send` rule) is in 0.1.0's promise (stable-surface §3.1).
  The `Async` effect **row element** is not in this bullet: it is accepted,
  shipped, and enforced like any other row element.
- **The wasm-gc backend.**
- **The capability authorization surface** — the `?` grade, the `Attempt[T, E]`
  that `perform?` returns, and preflight authorization. The entry keyword
  itself (`fn main allows ..`) is stable: it is the spelling the book teaches.
- **`Map[K, V]`'s generality.** The builtin map is String-keyed; an annotation
  naming a concrete non-String key is rejected where it is written. Completing
  it turns a rejection into an answer, which is a compatible change. A generic
  key type is unaffected, and `MutMap[K, V]` from `@vibe/core` is the generic
  map available today.
- **Line-granularity debugger stepping** and arbitrary-expression watch.

### 7.2 Withdrawn — not deferred

These were decided against on measurement, and 0.1.0 records that no measured
program needed them:

- **Borrow syntax.** The case it would exist for — returning a view of an
  argument rather than a copy — already works and already costs nothing. It
  would buy a spelling, not a capability.
- **Lifetime annotations.** They exist to make borrow syntax checkable. With no
  borrow syntax they annotate nothing.
- **Module-level `Ref`/cell.** Process-global mutable state is neither an
  effect-plus-handler (ADR-0021) nor invocation-local configuration (#1953),
  and a shared-nothing concurrency model has to answer what such a cell means
  across regions before it can have one.

Each stays refusable later on its own merits. What is recorded is that 0.1.0
does not ship them, not that they could never be right.

### 7.3 Removed, and not coming back under that name

- **`Result`** was removed from the language (#1324). Errors are the
  `Exception` effect; `Error` is deprecated at this freeze in favour of it.
- **The MoonBit host implementation.** `src/`, `moon.mod` and the `moon`
  toolchain are retired; nothing in 0.1.0 requires them.
- **The `V128` value type and its 12 `v128_*` intrinsics**, removed after
  measuring 22× an inline-wasm kernel with an unreclaimable 16-byte box per
  operation. Nothing here promises them.

### 7.4 Not promised, measured or otherwise

0.1.0 makes no promise about the per-module memory redesign, a new GC
representation, or complete async execution. Compiler size, mid-size memory and
incremental build KPIs are **observed**, not guaranteed.

## 8. Compatibility from here

- A proposed change to the stable surface (§2–§5 of
  [stable-surface.md](../user/reference/stable-surface.md)) must state its
  SemVer impact in an ADR.
- When something on the unstable surface settles, it moves into the frozen
  sections and enters the stable surface in the next Minor.
- Trait bound compatibility: **tighter bounds = Major, looser = Minor.**
- A comparison that 0.1.0 refuses later becoming a structural answer is a
  **compatible** change. An existing answer changing is **breaking**.
- Completing `Map[K, V]`'s generality is **compatible** — it turns a rejection
  into an answer.

## 9. Provenance

0.1.0's acceptance evidence is recorded on
[#2834](https://github.com/mizchi/vibe-lang/issues/2834): the seed release
verification, the registry round-trip, the book and stable-surface checks, the
full release gate, and the dry run of the release asset build itself. The
release is reproducible from the tagged commit plus the pinned seed, and the
pinned seed is reproducible from its own `source_commit`.

That evidence answers "is everything 0.1.0 promises present and working". It
does **not** answer "did anyone go looking for what is broken" — a checklist
can only confirm what someone already thought to write down, and this project
ranks silently-wrong above crashing. The `0.1.0-rc.x` rung exists to separate
those two claims, and the bug hunt that closes the second one is recorded with
the same evidence discipline.

The document that explains *what changed and why you would care* is
[release-notes-0.1.0.md](../user/getting-started/release-notes-0.1.0.md). This
one exists to say what you are holding.
