# Architecture Decision Log

A lightweight decision record: each entry records what was decided. For the
history behind a decision, read `git log` and the issue thread. The
user-facing surface these decisions freeze is
[stable-surface.md](../../user/reference/stable-surface.md).

---

## Status

- **accepted** — adopted and implemented.
- **partial** — implemented in part; the row names the current boundary.
- **proposed** — a pending decision or implementation, with an acceptance condition and an issue owner.
- **deferred** — outside the current release commitment.

## Rules for this log

New entries are written in English (AGENTS.md "Language and documentation
policy"); the existing Japanese rows migrate as they are revised.

**An ADR number is permanent and unique.** Numbers are cited from source
comments, fixtures, gate scripts, and other ADRs, so each must resolve to
exactly one decision. Never reuse a number, and **never start a per-section
number series** — the sections are a reading aid, not separate registries.
Until the 2026-08 cleanup the Tooling section ran its own series and collided
with Core on 0049 / 0050 / 0052 / 0053 / 0075; the two live entries were
renumbered to 0103 / 0104 and the three whose subject no longer exists were
deleted.

**Delete an entry whose subject no longer exists in the tree.** An ADR about a
removed script, flag, or toolchain does not become history by sitting here — it
becomes a false statement about the current build.

**`superseded` is a pointer, not an entry.** Fold what still holds into the
successor, mark it `(supersedes NNNN)`, and delete the old row. The old number
keeps resolving through that note, so a citation of it -- including one that
discusses it as the road not taken -- still lands on exactly one decision.

**Paths in older rows may point into the retired MoonBit host.** `src/**` and
any `.mbt` / `.mbti` file went away with that host (#594). Those citations are
kept as the historical record of where a decision landed at the time — they are
not navigation, and `scripts/check_doc_path_citations.sh` exempts them for that
reason. To find the code today, use `vibe symbols` / `vibe grep` rather than a
path written down years of commits ago.

**`proposed` says what would make it `accepted`.** A `proposed` entry that has
not moved in a release cycle is a decision nobody made: delete the row and keep
the idea in an issue, where triage can reach it.

| 0115 | **A line-leading `-`, `!` or `~` is a prefix operator when nothing separates it from its operand (Swift's rule, #3041).** A newline does not end an expression when the next line begins with a binary operator, so a block ending in a line `-1` used to parse as `<previous line> - 1`. When both lines were `Int` that compiled and answered the wrong value, and fixing it after the 0.1.0 freeze would have been a silent change of meaning. Now a token that can be a prefix operator is prefix when whitespace precedes it and none follows it: after an expression-ending token, a newline followed by a tight `-x` / `!x` / `~x` ends the statement (the lexer inserts the same synthetic `;` it inserts before a line-leading `(` or `[`). A subtraction that wraps keeps working as `- 1` (space after) at the start of the next line or with the `-` ending the previous line; every other line-leading operator (`+`, `*`, `\|>`, `&&`, ...) still continues. `->`, `-=` and `!=` are distinct tokens and never qualify. Only a newline counts as the whitespace before: on one line `a -1` stays a subtraction. `vibe fmt` keeps a line-leading `- 1` spaced (collapsing it to `-1` would change meaning), and the #2206 Unit-left-operand diagnostic names both edits (drop the space, or `(-1)`). Rejected: Go / Kotlin's rule (a leading operator never continues), which reformats every operator-first chain; freezing the old rule, which keeps the silent case. The compiler sources parse identically under both rules, so the committed seed builds this without a bump. Pinned by `fixtures/line_leading_prefix_op_test.vibe`, `lib/@vibe/compiler/tests/checker_minus_continuation_test.vibe` and `lib/@vibe/compiler/fmt/layout/layout_test.vibe`. | accepted |
| 0116 | **`for … in` collects, and a discarded result allocates nothing (#3043).** `for x in xs { body }` over an `Array` or another builtin collection stays an expression whose value is the `Array` of the body's results: there is no `for … yield`, and a bare `for` is not `Unit`. The compatible half is a promise stated in `syntax.md` and the cheatsheet: when the loop's value is discarded (a block statement followed by more statements, the last statement of a `while` body, or a branch of an `if` / `match` in such a position; a `handle` in such a position passes it to each arm, and to the handled body when no arm names `resume`, since a resumed handler receives the body's value) no result array is allocated. Binding the value, `let _ = for …` included, keeps it. Pull iterators stay statement-only (#1679). The linear backend implements it (`forin_discard_pass` plus the no-collect `compile_forin_loop` form, #1916), pinned by `fixtures/for_discard_no_alloc_test.vibe` and `for_discard_handle_no_alloc_test.vibe` in mid gate 40e3 on the bump lane: 252 B each, against 504,252 B for the same loop bound to a name. | 0117 | **Two spellings kept on purpose: `?` / `let*`, and `_` as pipe slot / section (#3044).** (1) `e?` returns `None` from the enclosing function (a closure's body is its own function); `let* x = e` makes the enclosing block `None` and the function carries on. That exit target is the reason both exist. In a function or closure body's own top-level block they exit to the same place and `?` is the one spelling there: `detect_top_level_let_star` makes a `let*` on that spine a warning naming `let x = e?` (both `vibe check` lanes and the build's warning rows). A `let*` in a nested block is legal in any function; the checker's railway rule used to demand an Option-returning FUNCTION for every `let*`, which refused exactly the nested use this row keeps, and now demands only that the block's value be an Option. (2) `_` keeps both roles, told apart by syntax alone: a bare `_` that is a whole argument of the call directly after `\|>` is the pipe slot (every such `_` receives the value), a `_` that is an operand of an operator makes the operator expression, up to the nearest enclosing call argument, a lambda section, and any other bare `_` is rejected. No separate pipe-placeholder token is added. Normative text: `syntax.md` and the cheatsheet. Pinned by `fixtures/try_let_star_option_test.vibe`, `fixtures/underscore_pipe_slot_section_test.vibe`, `fixtures/typecheck/underscore_bare_argument_reject.vibe` and `lib/@vibe/compiler/tests/warning_snapshots/let_star_top_level_test.vibe`. | accepted |
| 0118 | **`compare` returns the prelude enum `Ordering { Less; Equal; Greater }`, not an `Int` (#3042).** An `Int` of -1 / 0 / 1 had no exhaustiveness check (`match T::compare(a, b) { -1 => .., 1 => .. }` compiled without the `0` case) and nothing held a hand-written `compare` to three values; the decision had to be made before the 0.1.0 freeze, when changing it stops being cheap. `derive (Ord)` generates `T::compare(a, b) -> Ordering` (structs lexicographic over fields, a field of a declared type through its own `compare`; enums by variant order, then payload), and `@vibe/builtin`'s `String::compare`, `int_compare` / `float_compare` / `double_compare` / `string_compare` and the `minmax_by` / `maximum_by` / `minimum_by` (`_by_key`) comparators answer it too. `Ordering` is an ordinary enum rather than a checker-owned type: the checker checks the declaration ahead of every module that does not declare the names itself, and the lowering appends it once to a merged program that builds one, so `==`, `Show`, exhaustiveness and every backend treat it as a declared enum. | 0110 | **Importing a trait activates its namespace, never bare operation names (#2269, #2335–#2357).** `import pkg { trait Trait }` makes exported `Trait::*` companions visible, including operations derived from method-bearing trait declarations and explicit helpers associated with that trait. Aliasing the trait aliases the namespace (`trait Iterator as Iter` exposes `Iter::map`, not `Iterator::map`); bare `map` remains absent. Subtraits expose inherited methods through their own namespace, and generated operation names cannot be replaced by conflicting source declarations. This rule is general across traits. The standard finite indexed `Iterator[T]` demonstrates it: an implementation supplies `iter_length` and `iter_get`, while the exported `Iterator::map`, `filter`, `fold`, `find`, `any`, `all`, `iter`, and `flatmap` helpers work for every implementation. Array calls devirtualize to existing `Array::*` intrinsics, including through an imported alias, so the trait spelling has identical fuel, allocation, and code size to the direct Array spelling. Map iteration reads insertion-order key slots directly after a checked bound and never rebuilds `Map::keys` per element. Constructor-kinded parameters (`F[_]`) and constructor-indexed witnesses remain supported language mechanisms, but no constructor-polymorphic `Mappable` trait is part of the standard surface. Package contracts preserve parameter arity, and missing or duplicate implementations are checker errors before code generation. | accepted |
| 0105 | **`Int` is a 63-bit tagged value on i64, and overflow wraps as 63-bit two's complement on every backend (#1877, supersedes 0006).** One tag bit: the RC lane stores `n<<1`, so the range is **-2^62 .. 2^62-1**, the literal bound is 2^62-1, and a larger literal raises `IntLiteralOverflow`. ADR-0006 first reserved two tag bits (range -2^61..2^61-1); the shipped representation uses one, so the honest width is 63. The same in-range operands used to produce different values per backend with no diagnostic: untagged lanes (bump, wasm-gc) wrapped where i64 overflows (64-bit), while the RC lane's tagged `n<<1` wrapped `+`/`-` at 63 bits but `*` at 62 (its untag shift ran after the multiply) — silent-wrong, and even ops within one lane disagreed. Decision: (1) `+` `-` `*` `/` `<<` and unary minus wrap by sign-extending from bit 62 — identical values on bump / RC / wasm-gc. (2) The width follows the representation, so the RC (production default) lane wraps for free — its only change is untagging the multiplicand before the multiply ((t>>1)*u, same instruction count); untagged lanes renormalize with 2 branch-free instructions after the five ops (`%` / `>>` / bitwise ops are closed over in-range values), and chain-interior renorms are elided — a result feeding another wrapping op skips its renorm, since the renorm rewrites only bit 63 and wrapping ops derive result bits 0..62 from operand bits 0..62 alone, so only the chain's outermost renorm runs and per-op observed values are unchanged. (3) Trap-on-overflow was rejected (per-op cost, and wrapping is what hash/PRNG code wants); normalize-at-binding was rejected (breaks referential transparency: `let t = a*b; t/c` would differ from `a*b/c`). (4) `>>` is an arithmetic shift (it sign-extends); for a logical shift, mask afterwards. Bitwise `&` `\|` `^` `<<` `>>` and prefix `~` (#2344) are supported; `~` lowers to `x ^ -1` with a lane-dependent constant — tagged(-1) = `-2` under RC. Pinned by `lib/@vibe/compiler/tests/int_overflow_wrap_test.vibe` (all lanes) and the per-PR linear-vs-gc parity guard `bench/exec/int_wrap.vibe`. The committed seed carries the bound since seed/applied-trait-impl-2026-08-28, so the arithmetic spelling of large constants in `lib/**` (`(2305843009213693951 << 1) \| 1`) is no longer required. | accepted |
