# MoonBit verification, as practised by mizchi/veri

Surveyed 2026-09-23 from [mizchi/veri](https://github.com/mizchi/veri) (MoonBit
0.10.12, Z3 4.16, CVC5 1.3.4) and the MoonBit verification manual
(<https://docs.moonbitlang.com/en/latest/language/verification.html>).

## The pipeline

```text
MoonBit contracts / .mbtp proof files → Why3 theories → SMT-LIB 2 → Z3 / CVC5
```

A function carries its contract in a `where` block — the same place vibe
already puts `requires` / `ensures` (ADR-0064):

```moonbit
pub fn digit(value : Int) -> Int where {
  proof_ensure: result => 0 <= result && result <= 9,
} {
  @bounds.clamp(value, 0, 9)
}
```

The vocabulary, by frequency in veri: `proof_ensure` (534), `proof_require`
(327), `proof_import` (300), `proof_assert` (116), `proof_decrease` (33),
`proof_invariant` (28), `proof_pure` (18), `proof_external` (17). Logical
definitions (`predicate`, models) live in `.mbtp` files that are proof-only and
never compiled to runtime code. `#proof_external` maps a MoonBit type to a Why3
logical type and `#proof_import` maps a function to a Why3 symbol, which is how
`FixedArray[T]` becomes `map.Map` (`SmtArray[Integer, T]`) and `UInt` becomes
`bv.BV32`.

`moon prove` runs it. Proofs are **not** a runtime check: a `proof_require` is
an obligation on callers, discharged at verification time, and costs nothing
at run time.

## What veri adds on top: an honest verification practice

The library is less interesting for its lemmas than for the discipline around
them. Every piece below has a direct vibe counterpart that already exists or
is cheap to add.

1. **Model, implementation and runtime correspondence are three separate
   claims.** A logical model (`model(array) : SmtArray[Integer, T]`), a
   contracted implementation, and a runtime bridge that states which
   operations are proved to agree with the model (`model(add(x, y)) =
   bv.add(model(x), model(y))`). The architecture document has a table whose
   last column is literally "current guarantee", and it says "no" where the
   answer is no.
2. **Two integer preludes.** Every proof runs under mathematical integers and
   again under the machine-integer prelude, where arithmetic must avoid
   intermediate overflow. An adapter that wraps proves the wrap explicitly.
3. **Negative controls.** 68 deliberately false claims, sharded over four CI
   jobs, must remain unproved. A proof pipeline that accepts a false theorem
   is detected, not assumed away. (This is the same rule vibe's gate policy
   states as "a gate is trusted only once it has been shown to fail",
   #2248.)
4. **Differential tests fill every gap the prover cannot close.** Where the
   compiler cannot express a claim — MoonBit has no usable `old(...)`, and a
   `proof_let` snapshot crashes the compiler — the before/after contract is
   checked by QuickCheck against a snapshot reference, with fixed seeds and
   shrinking, and the document says it is *not* proved.
5. **Z3 as a reference oracle.** Expected values for FP and bit-vector
   operations are generated by Z3 and checked in (veri's vectors-check recipe
   detects staleness).
6. **Model checking for protocols.** `TaskGroup` from `moonbitlang/async` is
   modelled as a pure transition system; Z3 searches for temporal
   counterexamples, and traces from the real async runtime are replayed
   against the model. Counterexamples are saved, explained and minimized.
7. **An explicit trusted boundary.** Why3, the solver, MoonBit's translation
   and the `#proof_external` / `#proof_import` mappings are trusted; no custom
   axioms are added. `unknown` and timeouts count as unproved.

## Where aliasing bites

The most important finding for vibe's borrowing question is a limitation:

- **Why3 rejects aliased mutable arguments.** veri has to split
  `blit(source, target, …)` into `copy_within` (same array) and
  `blit_disjoint` (distinct arrays, verified); the dispatcher that picks one by
  object identity has no proof contract.
- **No `old(...)`.** Without a pre-state snapshot, "the cells outside the
  written range are unchanged" cannot be stated for a mutating function, so it
  is only tested.
- Reading an array cell directly inside an assertion made the compiler treat
  the mutating function as ghost code; veri wraps reads in named predicates
  to avoid it.

In other words: **verification of mutating code needs, before anything else,
a static guarantee that two mutable parameters do not alias, and a way to
name the pre-state.** Both are cheap if designed in; both are painful to
retrofit, which is exactly where MoonBit is today.

## Where associativity bites

veri's `algebra` package proves that a fold can be split into chunks, folded
left or right, and reordered **only** for operations supplied with proofs of
associativity (and commutativity for reordering), and it keeps a negative
control rejecting subtraction. That lemma is the correctness condition for a
vectorized reduction: a SIMD sum computes lane-wise partial folds and
combines them, which is a chunked, reordered fold. See
[borrowing-and-vectorization.md](borrowing-and-vectorization.md).

## Lessons for vibe

1. vibe's `where { requires, ensures }` already has MoonBit's surface; its
   Phase 1 lowers to runtime traps. Phase 3 (SMT) can follow veri's pipeline
   but should target SMT-LIB directly on a restricted subset rather than go
   through Why3 — vibe's value domain (63-bit wrapping `Int`, ADR-0105; byte
   strings, ADR-0098) maps onto `(_ BitVec 63)` and `(Seq (_ BitVec 8))`
   with less translation than MoonBit's. (Not onto SMT-LIB `String`, which is
   a sequence of code points — the same gap veri documents for MoonBit's
   UTF-16 strings.)
2. Design `old(e)` and a pre-state binder into the contract grammar **before**
   anyone writes a mutating contract.
3. Make "mutable arguments do not alias" a checked property of the language
   (the exclusivity rule in [mojo.md](mojo.md)), so the verifier never meets
   an alias.
4. Adopt the four-part practice wholesale: model + contract + runtime
   correspondence table + negative controls, with differential property tests
   (`lib/@vibex/quickcheck` exists) wherever a proof is out of reach.
